# 全局复用发现

目标：在写任何新代码之前，确认项目里是否已有可复用的实现。证据优先，不靠印象。

## 搜索顺序

下面只描述动作，用当前环境里能完成该动作的工具即可。

1. **广域探索**：环境支持子代理时，交给子代理做跨文件、跨命名约定的搜索，结果只取回路径与证据，不把大段代码带回主上下文。问题要具体，例如「项目里是否已有处理 SSE 分块解析的函数、HTTP 请求的安全封装、日期格式化工具，给出绝对路径和定义行」。不支持子代理时，用下面两步逐项完成，范围不缩小。
2. **精确文本搜索**：搜符号名、方法名、领域词，中英文都要试。例如 `parseSse`、`formatDate`、`重试`、`鉴权`。命令行可用 `rg -n 'formatDate|format_date'`。
3. **文件名搜索**：找 `util`、`helper`、`service`、`adapter`、`common`、`utils` 等模式，覆盖 `*.ts`、`*.js`、`*.py`、`*.java`、`*.go` 等项目实际语言。命令行可用 `rg --files | rg -i 'util|helper|common'`。
4. **目录结构**：列出模块的组织方式，判断复用应该去同模块、跨模块工具层，还是第三方依赖。

## 判定是否可复用

一个候选算可复用，需同时满足：

- **语义匹配**：做同一件事，而非只是名字相近
- **接口契合**：入参出参能用，或改造成本明显低于重写
- **无隐藏副作用**：不会带来不想要的 I/O、全局状态或耦合
- **契约可信**：调用约定清晰，不依赖隐含上下文

以下情况不要复用：

- 语义相近但契约完全不同，强行适配反而更复杂
- 带强业务耦合，复用到新场景会带入无关逻辑
- 性能或并发特性不匹配（例如同步函数用于高吞吐路径）
- 已有实现本身有问题，复用等于扩散缺陷；此时应修复原实现再复用

## 输出格式

搜索后给出简短清单，再决定动作：

```
候选 1: src/utils/http.ts:safeRequest
能力: 带超时与内网拦截的 HTTP 请求
改造: 需增加一个 header 参数，约 3 行
判定: 小改造复用

候选 2: src/common/retry.ts
能力: 通用重试
判定: 不可复用（项目约定错误不自动重试）
```

结论只能是三选一：直接复用 / 小改造复用 / 确实没有才新建。每个新建决定都要能回答「为什么现成的不行」。
