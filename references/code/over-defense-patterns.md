# 过度防御的典型模式与改写

以下模式是 AI 生成代码冗余的主要来源。识别后用右侧方式改写，保留必要的安全校验。

## 模式 1：内部可信数据重复校验

表现：数据已进入内部函数，入口处仍逐字段检查类型、非空、范围。

改写：校验放在系统边界（HTTP 入参、外部响应、反序列化结果）一次完成；内部函数直接信任契约，用类型系统或既有校验保证。

## 模式 2：空兜底链

表现：`value = data.get("x") or 0`、`return result or []`、缺字段就返回默认值。

改写：缺失代表异常时直接抛错，让上游感知真实状况。只有业务上确实「无值合法」时才用默认值，并写明理由。

## 模式 3：为未来预留的抽象

表现：只有一个实现却先定义接口、工厂、策略类；配置里加当前无人使用的开关；函数留一堆可选参数。

改写：删掉扩展点，直接写当前唯一实现。真实需求出现时再重构，成本通常低于提前抽象。

## 模式 4：层层 try-catch

表现：每个函数调用都包 try-catch，catch 里 `pass`、打日志后继续、或返回空对象。

改写：在能真正决策的层级捕获一次；处理不了就向上抛。禁止吞错和静默降级。

## 模式 5：不可能分支

表现：为「理论上不会发生」的状态写防御分支，增加阅读噪声。

改写：用断言或直接依赖不变量；若状态确实可能出现，应在上游修复而不是到处打补丁。

## 模式 6：防御性拷贝滥用

表现：每个函数入口都做全量深拷贝，担心被调用方改动。

改写：只在跨信任边界传递可变对象时拷贝；内部调用共享引用，靠约定和类型保证。

## 与安全底线的边界

以上克制只适用于「内部可信」场景。遇到下列情况仍必须严格校验，不属于过度防御：

- 来自用户、外部服务、第三方回调的输入
- SQL、命令、路径、URL 等可能造成注入或 SSRF 的参数
- 权限与归属判断
- 密钥、凭据的存在性与格式

判断口诀：**边界要硬，内部要简；错误要响，不要静。**
