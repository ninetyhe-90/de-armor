# 安全底线与信任边界

安全是 de-bloat 的硬约束。满足底线后，不再叠加与风险不匹配的防御。

## 六条底线

| 风险 | 必须做 | 典型错误 |
| --- | --- | --- |
| SQL 注入 | 参数绑定或预编译语句 | 字符串拼接 SQL |
| XSS | 按输出上下文转义 | 直接插入 HTML |
| 越权（AuthZ） | 校验权限与资源归属 | 只判断登录态 |
| SSRF | 目标白名单 + 内网地址拦截 | 直接请求用户给的 URL |
| 不安全反序列化 | 使用安全加载方式，不信任输入 | 直接反序列化不可信数据 |
| 机密泄露 | 密钥 token 从环境变量读取 | 硬编码或写进配置文件 |

## SSRF 内网拦截范围

对用户可控的目标地址，至少拦截：环回地址、`169.254.0.0/16` 元数据地址、私有网段，以及 `9.*`、`10.*`、`11.*`、`21.*`、`30.*` 段；IPv6 过渡与隧道地址同样拒绝。若业务确实需要访问内网，只允许管理员显式配置的白名单目标，并固定到解析后的 IP，避免 DNS 重绑定。

## 信任边界判定

- **外部输入**：HTTP 请求参数与 header、外部服务响应、文件内容、消息队列消息、用户上传——必须完整校验。
- **内部契约**：同进程内已校验的数据、类型系统保证的结构、可信配置——直接用，不重复校验。
- **跨边界传递**：进入另一信任域时重新校验，即使上游校验过。

## 不要用安全当挡箭牌

以下不是「更安全」，而是过度设计，应当拒绝：

- 对已经过校验的内部参数再加多层类型判断
- 为每个内部函数加 try-catch 并吞错，声称「防止崩溃」
- 因「安全」引入与威胁模型无关的框架、抽象层或配置开关
- 在不涉及外部输入的代码路径堆砌转义和过滤

真正的做法是：在边界把校验做对做全，在边界内保持代码简洁可审计。
